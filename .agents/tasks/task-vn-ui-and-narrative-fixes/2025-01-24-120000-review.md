# VN UI polish and character name reveal system

This change bundles two categories of work: engine/UI quality-of-life improvements (text control bar labels, named saves, backlog search, backlog persistence, message rollback) and a narrative feature that hides character names behind "???" until they are revealed in-story, with a conditional branch fork for the unnamed-Mira path through the dining scene and Night-naming dialogue.

Watch for: unbounded history stack growth during long play sessions (confirmed), save-file size bloat from serializing the full backlog in every history snapshot (confirmed), and the backlog search input leaking event listeners on repeated opens (confirmed).

## High-level view

The control bar switches from emoji to text labels and gains a Back button. Save slots now prompt for a custom name and display it, with a rename button on filled slots in save mode.

The name-reveal system adds a `revealedNames` map to engine state and a `reveal_name` step type. Characters without `revealExempt: true` display as "???" until a `reveal_name` step fires. The no-name branch for Mira is handled by a router scene (`ch02_dining`) that forks into `ch02_dining_named` / `ch02_dining_unnamed`, and the Night-naming dialogue splits similarly via sub-scenes.

The rollback mechanism snapshots the full engine state (including the full backlog array, deep-copied) before every say/narration/thought step, storing them in an in-memory `historyStack`. This gives correct undo semantics but carries a memory cost proportional to step count times backlog length.

Backlog persistence is achieved by including the backlog array in `snapshot()` and restoring it in `restore()`, so saves now carry dialogue history. The search input in the backlog modal is wired fresh each time `showBacklog()` is called, leaking listeners on repeated opens.

<details>
<summary>Issues (5)</summary>

1. **History stack memory growth** — `historyStack` grows by one full snapshot (including deep-copied backlog) per dialogue step and is never capped. After hundreds of steps the memory cost becomes significant. Add a cap (e.g., 50-100 entries, shift oldest out).
2. **Save payload size** — Each snapshot deep-copies the entire backlog array. A 200-entry backlog serialized into each of potentially hundreds of history entries is wasteful. Consider storing backlog separately or using an index/delta approach for history snapshots.
3. **Backlog search listener leak** — `showBacklog()` adds a new `input` event listener to `#backlog-search` on every call without removing the previous one. Over repeated opens this stacks duplicate handlers. Use `{ once: true }` cleanup, or detach the old listener before attaching.
4. **Quick-save bypasses name prompt** — `quickSave()` calls `save(0)` with no `customName` argument, so slot 0 always gets the scene ID as its name. This is probably intentional but inconsistent with the user-facing save flow.
5. **Missing reveal for Night** — `night` is not in `revealExempt` and no `reveal_name` step fires for Night in ch03_tame_night. Night's speaker label will show as "???" for all dialogue after taming until (if ever) a reveal is added later.

<summary>Details</summary>

## History stack and memory pressure

Every `doSay`, `doNarration`, and `doThought` call pushes a full `snapshot()` onto `historyStack`. The snapshot includes a `JSON.parse(JSON.stringify(state.backlog))` deep copy. After 300 dialogue steps with a 200-entry backlog, that's 300 copies of up to 200 objects living in memory simultaneously. The stack is cleared on `reset()` but never trimmed during normal play.

```js
function doSay(step) {
  historyStack.push(snapshot()); // full deep copy every step
  ...
}
```

A simple ring-buffer cap (e.g., `if (historyStack.length > 100) historyStack.shift()`) would bound memory without losing practical undo depth. Alternatively, the backlog could be excluded from history snapshots since it can be reconstructed by trimming entries from the current backlog.

## Backlog search listener accumulation

`showBacklog()` grabs `#backlog-search` by ID and attaches a new `input` listener each time the modal opens:

```js
searchInput.addEventListener("input", function onSearch() { ... });
```

Since the modal's `entries.innerHTML` is reset on each open (destroying the old entry DOM nodes), the filtering closure holds references to stale `entryElements`. After N opens, N listeners fire on each keystroke — the first handles current elements, the rest iterate over garbage-collected arrays (harmless but wasteful). Clearing the listener on modal close or using a single persistent handler would be cleaner.

## Missing reveal_name for Night

The character `night` is not marked `revealExempt` in `characters.js` and no `reveal_name` step is present in `ch03_tame_night` or its sub-scenes. After taming, Night speaks dialogue — that dialogue will render with "???" as the speaker name. This appears to be an oversight since the scene explicitly establishes Night's name during the taming sequence. A `{ type: "reveal_name", char: "night", name: "Night" }` step should fire after the naming exchange.

## Unnamed-path Mira reveal as "Slave"

In `ch02_dining_unnamed`, the reveal step fires `{ type: "reveal_name", char: "mira", name: "Slave" }`, transitioning Mira's speaker box from "???" to "Slave". This is a deliberate narrative design that reflects the world's treatment of her in the no-name branch. Worth noting that this reveal persists through the entire remainder of the game unless overwritten by a later `reveal_name` — no such later reveal exists on the unnamed path, so "Slave" is permanent for that playthrough.
